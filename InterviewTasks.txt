과제 개요: 사내 직원 관리 시스템 (Internal Employee Portal)
────────────────────────────────────────

비트컴퓨터(국내 기업)의 사내 직원 관리 웹 애플리케이션을 구현해 주세요.
직원용 UI와 관리자(Admin) UI가 구분된 웹 애플리케이션이며, AI와 클라우드를 적극적으로
활용하여 개발해 주시기 바랍니다.


────────────────────────────────────────
시간 안내
────────────────────────────────────────

· 작업 시간은 총 6시간을 기준으로 합니다.
· 단, 아래 [측정] 항목의 스크립트 실행 대기 시간은 작업 시간에 포함하지 않으셔도 됩니다.
· 제출은 과제 수신 후 1주일 이내에 해주시면 되며, 그 안에서 시간 배분은 자유롭게 하십시오.
· 완성도보다 판단의 근거를 봅니다. 6시간 안에 다 넣기 어렵다고 판단되면
  무엇을 넣고 무엇을 뺐는지 적어 주시면 됩니다. 범위를 줄인 것은 감점이 아닙니다.


────────────────────────────────────────
1. 기능 요구사항
────────────────────────────────────────

· 로그인 UI

· 직원용 UI (User Portal)
  - 로그인한 직원이 자신의 개인 인적사항을 조회하고 수정할 수 있는 기능

· 관리자용 UI (Admin Dashboard)
  - 새로운 직원 계정을 생성하는 기능
  - 전체 직원 목록 및 개별 상세 정보 조회
  - 직원의 퇴사 처리
  - Background Check API 연동 — 관리자가 배경 조회 결과를 확인할 수 있어야 합니다
    (API 명세는 첨부 swagger.yaml 참조)
    ※ 이 API는 모든 요청에 X-Candidate-Key 헤더가 필요합니다.
      키는 과제 안내 메일에 적어 두었습니다. 지원자마다 키가 다르며,
      본인 키로 만든 데이터만 조회됩니다(다른 지원자와 섞이지 않습니다).

· 접근 권한
  - 직원은 자신의 정보만 조회·수정할 수 있어야 합니다
  - 관리자 전용 기능(계정 생성, 전체 목록 조회, Background Check 등)은 관리자만
    사용할 수 있어야 합니다
  - 퇴사 처리된 직원의 시스템 접근은 통제되어야 합니다
  - Background Check 결과 등 민감정보는 권한에 맞게 다뤄 주세요


────────────────────────────────────────
2. 명세에 정하지 않은 것 — 직접 판단해 주세요
────────────────────────────────────────

아래 항목들은 의도적으로 정해두지 않았습니다. 정답이 있는 문제가 아니며,
무엇을 택하셨는지와 그 이유를 보려는 것입니다.

  (1) 퇴사 처리된 직원의 접근을 언제부터, 어디까지 막을 것인가
      - 퇴사 시점을 어떻게 다룰지, 이미 로그인해 있는 세션은 어떻게 할지 등

  (2) Background Check를 언제 실행할 것인가
      - 계정 생성 시 자동인지, 관리자가 직접 실행하는지, 다시 조회할 수 있는지 등

  (3) Background Check 결과를 얼마나 보관할 것인가
      - 민감정보의 보존 기간과 열람 통제를 어떻게 볼 것인가

  (4) 직원이 자신의 정보를 수정할 때 별도의 절차가 필요한가
      - 즉시 반영인지, 승인이 필요한지, 이력을 남길 것인가

이 중 최소 3개에 대한 판단을 아래 [제출물 3]에 적어 주세요.

4. 제출물
────────────────────────────────────────

[제출물 1] 동작하는 애플리케이션

  · 접속 가능한 배포 URL (로컬 실행 아님)
  · 관리자 계정 1개, 일반 직원 계정 1개 (아이디 / 비밀번호)
  · 소스코드 (GitHub 등 저장소 링크 또는 압축 파일)

  ※ 평가는 완성된 앱을 저희가 직접 사용해 보며 진행합니다.
    제출 후 배포 상태를 유지해 주세요.


[제출물 2] MEASUREMENTS.md — API 실측 결과

  첨부 API의 실제 거동은 명세에 적혀 있지 않습니다. 직접 호출해 확인한 뒤
  아래를 정리해 주세요. 모든 수치에 표본 수를 함께 적어 주세요.

  · GET /background-checks/{checkId} 응답 지연 — p50 / p95 / p99 / 최댓값
  · HTTP 상태코드 분포 (코드별 비율)
  · 같은 employeeId 로 POST 를 반복하면 어떻게 되는가
  · pending 에서 최종 상태까지 걸리는 시간
  · 동시 요청 수를 늘렸을 때 거동 변화가 있는가
  · 첨부 명세(swagger.yaml)와 실제 동작을 대조한 결과
    - 명세에 적혀 있으나 실제로는 확인되지 않은 것이 있었는가
    - 명세에 없으나 실제 호출에서 발견한 동작이 있었는가
    - 명세에 적힌 값이 실제 상황에 맞지 않는다고 판단한 것이 있었는가

  그리고 위 실측값을 근거로 아래를 정하고, 각각 왜 그 값인지 써 주세요.

  · 타임아웃  · 재시도 횟수와 간격  · 폴링 주기  · 재시도를 중단하는 조건

  ※ "일반적으로 권장되는 값"은 근거로 보지 않습니다.


[제출물 3] DECISIONS.md — 설계 판단

  위 [2. 명세에 정하지 않은 것] 중 3개 이상을 골라, 각각 아래 네 가지를 써 주세요.
  항목당 200자 내외면 충분합니다.

  · 무엇으로 정했는가
  · 왜 그렇게 정했는가
  · 반대로 정했다면 어떤 장점이 있었는가
  · 이 선택이 틀리는 상황은 어떤 경우인가


[제출물 4] AI_LOG.md — AI 협업 기록

  AI와 대화한 전체 내용을 파일로 첨부해 주시고, 추가로 아래 세 가지를
  별도로 정리해 주세요.

  A. AI의 제안을 거절하거나 되돌린 지점 3개
     · AI가 제안한 것 / 내가 대신 택한 것 / 그렇게 판단한 근거

  B. AI가 처음에 잘못 만들어서 고친 지점 (1개 이상)
     · 무엇이 틀렸는지, 그리고 그것을 어떻게 발견했는지
       (테스트 / 로그 / 실측 / 코드 리딩 중 무엇으로 발견했는지)

  C. 이 코드에서 지금 본인이 가장 설명하기 어려운 부분 1개
     · 왜 그렇게 되었는지 솔직하게 적어 주세요. 감점 항목이 아닙니다.

5. 평가 방식 (미리 알려드립니다)
────────────────────────────────────────

평가는 두 단계로 진행됩니다.

  1단계 — 제출하신 앱을 저희가 직접 사용해 봅니다.
          제출 후 배포 상태를 유지해 주세요.

  2단계 — 온사이트 인터뷰에서 제출하신 코드를 화면에 함께 띄워놓고 질문드립니다.
          · MEASUREMENTS.md 의 수치와 그것으로 정하신 값에 대해 여쭤봅니다
          · DECISIONS.md 에 적으신 판단과, 반대 선택의 장점에 대해 여쭤봅니다
          · 코드의 특정 부분을 왜 그렇게 두셨는지 여쭤봅니다

따라서 과제를 진행하실 때, 만드신 결과물의 구조를 본인이 설명할 수 있는 상태로
두시는 것이 중요합니다.

AI를 많이 쓰신 것 자체는 전혀 문제가 되지 않습니다. 저희도 그렇게 개발합니다.
다만 본인이 무엇을 왜 그렇게 두었는지는 아셔야 합니다.
모르는 부분은 [제출물 4]의 C 항목에 미리 적어 주시면 됩니다. 그것을 솔직하게
적어 주시는 편이, 면접에서 설명하지 못하시는 것보다 훨씬 좋은 평가를 받습니다.
